# 反馈工单处理流程

本流程用于健康档案反馈工单的排查与修复，配合 [Agent 工作规范](../AGENTS.md) 执行。用户要求处理、排查或继续查看一个工单时，默认贯穿下列五步；明确要求只分析或暂不修改时，停在授权范围内，并如实记录进度。

## 1. 读取工单，在本地导入报告

- 读取工单编号、问题描述、复现步骤、全部附件、提交时环境及已有处理记录，先确认是否已被处理。
- 区分报告原件、报告截图和应用问题截图。优先使用用户上传的报告附件；只有问题界面截图时，不把界面截图当作检验报告上传。
- 确认本地已启动的环境和端口，创建或复用以反馈单号命名的健康成员（用户所说的“角色”，如 `Bxxxx`）。通过现有上传界面或正常上传 API 将报告导入该成员，使用户能在本地应用中直接找到并查看。
- 保存工单号、成员、报告之间的本地对应关系；继续排查时复用已有记录，避免重复创建成员或上传。只保存在私有本地工作记录中，不提交附件、数据库或健康内容到仓库。
- 对照应用版本、OCR 引擎、模型和视觉开关。沿用用户授权的 AI 链路；已要求只用文字模型时，不擅自开启视觉或发送给其他模型。环境不一致须明确记录，不把替代环境验证称为原环境完整复现。

## 2. 对照反馈验证本地结果

- 通过正常解析流程复现用户描述，核对原件、OCR、AI 验收、实际入库和界面显示，定位问题发生在哪一层。
- 逐项检查遗漏、重复、结果及单位、标准化、检查归属、日期和趋势资格。区分“指标待核对”“检查时间待确认”和“报告待归档”，不能只以待核对数量下降判断修复成功。
- 区分已复现事实、初步原因和未验证假设。隔离脚本可用于定位，但不能替代本地应用中正常流程的最终验证。

## 3. 有初步结论后更新为“处理中”

及时更新工单，不等修复结束才登记。回复自然、简洁，简要解释问题原因和当前处理进度；原因尚未证实时明确为初步判断。不展开内部排查过程、原始 OCR、模型响应或具体健康结果。

示例：

> 初步排查发现，识别后的部分指标名称与报告原文存在字形差异，系统没能正确对应，导致检查时间显示为“待确认”。正在调整匹配逻辑，并使用您提供的报告验证。

常规进度使用后台支持的合法流转，并核对保存结果；不把“已确认”当作开始修复后的最终进度。服务不可用时如实告知更新未完成，不宣称已保存。

## 4. 最小修复，再重跑同一报告

- 优先修复同类问题的共同原因，保留数值、日期、标本、方法和多结果列等必要边界，避免为单份报告放宽所有验收规则。
- 补充合成数据回归用例，检查其他报告场景；不把真实报告或结果写入测试、日志或示例。
- 每次完成设计或实现后进行消融实验，确认各项改动的必要性，去掉无效分支、不必要的抽象与设计。涉及 OCR 或 AI 调用变化时，记录额外调用次数和可获得的 token 用量，不新增无依据的多轮重试。
- 使用本地应用的正常重处理流程重跑同一份报告，核对实际保存结果、重复项、检查归属及趋势资格。保留重跑前后必要的私有证据；不直接改正常指标、日期或确认状态来制造通过结果。
- 更新必要文档和当前 Unreleased 修复说明，执行相关测试、类型检查或构建及 `git diff --check`。修复任务本身不授权发版、升版本或数据库编号。

## 5. 修复验证完成后更新为“已修复，待发布”

填写包含修复的迭代版本，按“简要原因、已做的修复、实际验证情况、发布进度及必要的下一步”说明。版本以仓库当前迭代及发布计划为准，不为填工单临时升版；尚未确定的发布时间或效果不作承诺。

示例：

> 排查发现，识别后的部分指标名称与报告原文存在字形差异，系统没能正确对应，导致这些指标的检查时间显示为“待确认”。相关匹配逻辑已修复，并用您提供的报告完成本地验证，预计随 x.y.z 发布，升级后可重新解析报告验证效果。

- 示例仅用于表达方式，原因、结论和下一步必须与本次事实一致。未覆盖原环境或仍有待验证的问题，要用一句话说明，不把局部验证写成完整修复。
- OCR 行数、测试数量、消融过程、AI 调用次数等保留在内部记录，不写入常规用户回复。内部状态纠正不逐步向用户播报，确需说明时简短告知当前准确状态，保留真实审计记录。

- 尚未发布，一律不直接标记“已解决”。发布后再按实际发布和验证情况流转为“已发布，待验证”或“已解决”。
- 工单仍有关键问题未修复或未验证时，保持“处理中”，说明剩余事项；不能用一条验证边界备注替代关键路径验证并宣称全部完成。
- 保存后重新核对状态、修复版本和处理记录，最终向用户提供工单链接、本地报告入口、验证结论及仍需原环境验证的事项。

误选状态需要纠正时，优先使用已有纠正能力，不为绕过流转限制连续登记无业务意义的状态。确需直接修正数据库时，先核对表结构及关联操作，备份受影响记录，在事务内同步当前状态、处理记录、更新时间和并发版本等必要数据，并验证前后的一致性；保留真实审计，不删除用户内容或伪造发布事实。
