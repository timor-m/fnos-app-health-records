# AI 能力架构

健康档案将 AI 能力拆分为运行时、任务路由和领域实现三层。当前只有“报告结构化整理”正式接入，报告摘要、指标解释、形态发现整理和重复报告辅助判断已登记为预留场景，不会在未实现时被调用。

## 分层职责

### AI Runtime

`packages/server/services/ai-runtime.service.ts`

- 调用 OpenAI-compatible Chat Completions 接口。
- 处理鉴权、超时、网络错误、上游状态码和响应正文提取。
- 统一返回模型、结束原因、Token 和耗时。
- 不包含报告、指标、形态发现或其他健康领域逻辑。

### AI Task Registry

`packages/server/services/ai-task-registry.ts`

- 为每个 AI 场景定义稳定的 `taskKey`、名称、说明、模型角色和响应模式。
- 明确场景是否已经实现，未实现任务调用时返回 `AI_TASK_NOT_IMPLEMENTED`。
- 作为设置页和服务端任务路由的共同来源，避免前后端分别维护场景列表。

当前任务：

| taskKey | 场景 | 状态 |
| --- | --- | --- |
| `report_extraction` | 报告结构化整理 | 已实现 |
| `report_summary` | 报告内容摘要 | 预留 |
| `health_explanation` | 指标通俗解释 | 预留 |
| `morphology_extraction` | 形态发现整理 | 预留 |
| `duplicate_assistance` | 重复报告辅助判断 | 预留 |

### AI Task Service

`packages/server/services/ai-task.service.ts`

- 根据 `taskKey` 读取该场景绑定的连接配置（profileId）和模型。
- 未单独绑定时继承默认连接配置和其文本模型。
- 校验场景开关、API Key 和模型配置。
- 将通用请求交给 AI Runtime 执行。

### 领域实现

报告结构化整理位于：

- `packages/server/services/ai-extraction.service.ts`
- `packages/server/services/ai-extraction-orchestrator.service.ts`

领域层负责提示词、输入规划、输出结构校验、OCR 证据匹配、重试策略、结果合并和数据库写入。通用 Runtime 不理解这些规则。

视觉复核位于 `packages/server/services/ai-vision-review.service.ts`：文本解析与遗漏补提取结束后仍有未确认指标候选时，把对应页面图（经 OCR worker 渲染为受控尺寸的 JPEG）发送给连接配置的视觉模型逐行核对；表格结构模型失败（no_structure/failed/partial）的页会把疑似被规则误丢的测量形噪声行一并列入候选。返回的指标必须逐字回指服务端筛出的 OCR 行才可合并入库，证据标记 `source: "vision"`；归一化证据闸门对纯视觉来源跳过数值/单位回指，因为复核的意义正是修正 OCR 误读。仅"详细"解析程度触发，单份报告默认最多 3 页（`AI_VISION_REVIEW_MAX_PAGES`，0 为停用），复核失败不阻断文本解析结果。

## 报告内容分类与提示词路由

报告整理在调用模型前先由 `report-content-classifier.service.ts` 对脱敏后的 OCR 内容做本地规则分类，不新增一次 AI 请求。分类覆盖体检、检验、影像、功能检查、病理、门诊、住院、处方、票据、疫苗和其他资料；分类置信度不足时回退到通用提示词，任何分类结果都不能跳过原始页面。

分类分为两层：

- 文档级主类型用于确定整份档案的报告类型。包含封面、总检结论及多个科室章节的综合资料保持为“体检”，不会被其中一页检验单或影像结果覆盖。
- 页面或解析单元级类型用于选择提取插件。综合体检中的检验页、影像页仍分别使用检验和影像约束；单页检验单、处方、票据等则同时作为文档类型和单元类型。

OCR 重建后的每一行会先标记为元数据、表头、章节标题、定量/定性指标、形态发现、叙事正文、噪声或待判断内容。原始 OCR 始终保留；用途分类只决定派生 AI 输入，不会修改原始结果。字典唯一命中、表头列关系明确且 OCR 置信度可靠的表格行会在本地直接形成高可信指标，AI 无权删除或改写；其余歧义指标继续交给模型，低可信内容保留到待核对链路。

提示词版本为 `health-record-routed-v4`，解析规划版本为 `ocr-unit-plan-v9`。每个请求只组合最小公共约束、当前内容类型提示和当前路由的输出契约，不再让检验单元重复携带处方、票据、疫苗和形态发现等无关 Schema，也不再在 OCR 正文后重复追加候选原文。服务端预分类只用于选择提示词，不会作为 OCR 正文提交给模型，避免内部枚举被复制为报告字段。

结构化整理使用四种路由：

| 路由 | 输入范围 | 允许输出 |
| --- | --- | --- |
| 文档概况 | 总检/出院/病理结论锚点、元数据、章节目录和首页标题 | 标题、报告类型、机构、日期、科室、编号和部位等公共字段 |
| 指标 | 本地尚未可靠解析的指标行、最近章节和表头 | `observations` |
| 形态 | 形态候选及相邻原文 | `morphologyFindings` |
| 叙事 | 住院经过、出院医嘱、病史、病理所见、总检结论等章节 | 诊断、用药、操作、费用及 `report_structured_sections` |

文档概况按“关键结论锚点 → 元数据和章节目录 → 首页内容”选择上下文，避免长报告只根据第一页生成片面标题。未超限的单页报告可合并文档概况与指标提取，避免额外调用；超大单页仍保留独立完整指标单元，不为凑字符上限截断原表格。没有指标候选但包含医疗叙事的页面仍会生成叙事单元。

内容类型对应的主要结构化信息如下：

| 内容类型 | 主要结构化内容 |
| --- | --- |
| 体检 | 套餐、基础测量、分项发现、总检结论和明确复查要求 |
| 检验 | 标本、项目、结果、单位、参考范围、异常标记和方法 |
| 影像/功能检查/病理 | 检查方式、部位、所见、结论、形态发现、分级或病理诊断 |
| 门诊 | 主诉、病史、诊断、处置、诊疗操作、用药和医嘱 |
| 住院 | 入出院信息、诊断、手术操作、住院经过、出院用药和医嘱 |
| 处方 | 药名、规格、剂型、剂量、频次、途径、疗程、数量和用法 |
| 票据 | 票据号、总额、医保、自费、费用分类和明细 |
| 疫苗 | 疫苗名称、剂次、厂家、批号、接种日期、部位和下次日期 |

诊断、药品、诊疗操作、疫苗和费用分别写入独立领域表；体检、检验、影像、功能检查、病理、门诊和住院中不适合进入趋势的类型专属原文章节写入统一的 `report_structured_sections`。章节使用固定白名单 `sectionKey`，保存显示标题、完整原文和 OCR 证据，不让模型生成解释或诊断。只有符合定量或定性指标契约的数据写入 `observations` 并参与趋势。所有专属事实都必须携带当前单元内可验证的页码和 OCR 原文证据，最终与公共字段、指标和形态发现一起原子写入。

专属事实和报告专属章节均支持人工新增、校对和删除。人工操作以整项为保护边界：后续 AI 重跑只替换未保护的 AI 行；人工修改项通过业务身份、固定章节键或原 OCR 证据匹配，避免模型再次写入修改前的重复记录；人工删除项保留软删除抑制标记，防止同一证据被自动恢复。报告详情不展示软删除项，但审计日志保留操作类型、报告和字段范围，不记录诊断、用药或章节正文。

解析单元的分类版本、主类型、候选类型、置信度和原因保存在 `ai_extraction_unit_routes`。单元事件同时记录 document、scalar、morphology 或 narrative 路由，便于在详细处理日志中理解实际调用目的。AI 审计只展示模型、类型、Token、耗时和状态，不记录 API 地址、OCR 正文或模型响应正文。

## 配置与凭据

连接配置和场景绑定存储在现有 `app_settings` 的 `ai.provider` JSON 中：

- 连接配置以 `profiles` 列表保存，每份包含 id、名称、Provider 预设 key、API 地址、文本模型、视觉模型和加密后的 API Key；Provider 预设 key 用于驱动平台差异（如 MiniMax 视觉限制、Ollama 免 Key）。
- API Key 继续使用应用私有密钥加密，场景绑定不会复制密钥。
- 场景只保存可选的 `profileId` 和 `model`，默认模型通过 `defaultProfileId` 引用具体配置。
- 删除连接配置时校验是否仍被默认模型或场景绑定引用，避免悬空引用。
- 旧版本按 Provider 独立保存的配置在读取时自动迁移为 `legacy_<provider>` 稳定 id 的连接配置并回写，场景绑定的 `provider` 映射为 `profileId`，不需要数据库迁移。

## 新增 AI 场景

1. 在 `AiTaskKey` 和 `aiTaskRegistry` 注册稳定任务键，开发期间保持 `implemented: false`。
2. 在独立领域服务中定义输入、提示词、输出 Schema、证据校验和降级策略。
3. 通过 `executeAiTask(taskKey, request)` 调用模型，不直接发起 `fetch`。
4. 为任务增加审计语义、超时与错误映射测试，禁止记录请求正文、患者个资和 API Key。
5. 完成端到端验证后将任务标记为 `implemented: true`，设置页会自动开放独立模型绑定。

若新场景需要独立任务状态、结果历史或结构化审计，再新增版本化数据库迁移；仅新增 Provider/模型绑定不需要迁移。

## 约束

- Runtime 不能引用健康报告领域类型。
- 领域提示词和输出解析不能放进 Runtime 或设置服务。
- 新场景必须通过任务注册表调用，不能复用 `report_extraction` 伪装成其他用途。
- AI 输出必须由领域服务校验，不能直接写入报告、趋势或提醒。
- AI 审计只记录任务、模型、Token、耗时、状态和错误摘要，不保存 OCR 正文或 AI 响应正文。

## 补充报告页

`page-append-v1` 复用现有 processing_jobs 和整份报告 extraction planner。草稿 OCR 不进入正式页面查询；发布后用全量有效 OCR 规划 AI 单元，重试复用同任务检查点。持久化在证据过滤和人工覆盖之后执行旧记录保留校验；缺失/改变旧结果会回滚所有结构化表，不把部分成功当作完成。参见 [流程与边界](REPORT_PAGE_APPEND.md)。
